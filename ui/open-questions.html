Package Protector — pre-build review

Open questions before build

The mockup is done and every screen works end to end — but it works by standing in for three real contracts nobody has confirmed yet. Below is what's been faked, grouped by who actually needs to answer it.

04.09.2026 Prototype: complete, RTL, 500+ mock deliveries Nothing here blocks demoing further

Business & product 5 questions

Calls the prototype had to make on its own to keep moving. None are technical — they're policy.

Delivery lifecycle

  1. Can a submitted delivery ever be reopened — say, to add a package that was missed at shipping? mockup assumes: no. Submitted is final; a missed package means a new delivery.

Manual review outcomes

  1. When a manager confirms a flagged package was actually fine — or really was opened — does that decision need to reach anywhere outside the app (an incident log, a carrier claim, a compliance record)? mockup assumes: the note stays on the package. Nothing downstream.
  2. Does a confirmed-opened package trigger anything automatically — notify security, hold the shipment, alert the customer? mockup assumes: nothing. It's a red badge on a list, waiting to be read.

Roles

  1. Are Employee and Inventory Manager mutually exclusive, or can one person hold both in Keycloak? mockup assumes: doesn't matter yet — nothing is role-gated in the prototype.

Photo requirements

  1. Is "4+ photos, any image file" actually the bar, or does this need defined angles / lighting before it's real? mockup assumes: any 4+ image files pass. No content checks at all.

The tamper-detection API developer 9 questions

The whole point of the app runs through this call, and every bit of it is currently a 1.8-second timer and a dice roll.

Request shape

  1. Input format — raw image files, URLs, or base64? Any size, resolution, or format ceiling (JPEG/PNG, max MB)?
  2. How are pre-ship and post-receive images paired — exact positional matching per angle (front-before ↔ front-after), or two unordered sets it correlates itself?

Call semantics

  1. Synchronous (call and wait), or async (submit a job, then poll or get a webhook)? What's typical latency in practice? mockup assumes: a flat ~1.8s delay, no polling, no webhook.
  2. Retry / idempotency if a call errors — safe to resend the same photos, or does it need an idempotency key to avoid double-billing or duplicate jobs? mockup assumes: an unlimited manual retry button. No dedup logic at all.

Output & auth

  1. Output shape — boolean, confidence score, per-image detail, annotated images back?
  2. Does the API itself decide "inconclusive," or is that a confidence threshold Package Protector has to define on its own? mockup assumes: inconclusive is just a third flat outcome. No threshold logic exists.
  3. Auth mechanism for calling it — API key, OAuth, mTLS?
  4. Rate limits, cost per call, and max batch size?
  5. What images actually get sent back or logged on their side — any data-retention concern to flag to legal?

Other system owners 2 questions

Different people than either group above, but their answers block the same build.

ERP (Oracle) owner

  1. Does the ERP view actually expose the shipment → PO link end to end, and is it always 1:1 — or can a shipment have no linked PO? mockup assumes: yes, always present. The PO auto-fills the moment a shipment number validates.

Internal storage service owner

  1. Upload contract (what do we send, what comes back — an id, a URL?), retrieval contract, auth, size/format limits, retention and delete support? mockup assumes: photos live as in-browser blob URLs. Nothing is actually persisted anywhere.

None of this blocks continuing to demo the prototype — every item above already has a working stand-in, which is exactly why the walkthrough holds together end to end.

But each answer changes something real once the build starts: the API contract shapes the entire backend integration layer, the ERP linkage shapes the create-delivery form as shipped, and the business calls decide what "done" actually means for the manager's review flow.
